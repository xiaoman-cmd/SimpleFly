# SimpleFly 开发笔记

> 开发过程、实现权衡、故障排查与逐版本变更。使用说明见 [README](../README.md) 与 [用户手册](../用户手册.md)。

## 版本变更总览

「装好了但系统设置里看不到」的两个病因都修掉了，排查过程见 下文「故障排查」：
- **0.1.0** —— `Info.plist` 缺 `ComponentInputModeDict`、bundle id 不是三段式，TIS **静默忽略整个 bundle**
- **0.2.0** —— `InfoPlist.strings` 的 key 少了 `.SimpleFly` 一段，显示名退化成一串 `com.simplefly.inputmethod.SimpleFly.Hans`，**列表里其实有、只是认不出来**
- **0.2.2** —— 图标是 128×128 px、72dpi 的 TIFF，逻辑尺寸被当成 **128 pt**（对照物应取系统「简体拼音」的 22×16 pt），所以显得巨大
- **0.3.0** —— 候选窗按鼠须管的 `metro` 主题重绘，补上标点输入、中英一键切换、内嵌编码
- **0.3.1** —— 「图标是一整块黑方块」：菜单栏图标是**模板图渲染**（系统只看 alpha、自己涂成单色），
  「不透明底 + 不透明白字」会被涂成纯黑一块。改成**底板 + 字形挖空**（和鼠须管、和系统日本语输入法的「あ」同一种画法），见 下文「故障排查」
- **0.4.0** —— 三项新功能（见 README「键位与行为」）：
  **自定义快捷输入**（`abc = 测试短语`，改文本文件即生效）、
  **方向键选候选**（↑↓←→ 移动高亮，空格/回车/逗号顶屏都跟着走）、
  **查编码**（`Ctrl+/` 后用拼音查字，候选上直接标出音形码拆分，如「好 hc·nz」）
- **0.4.1** —— 「输入源列表里图标是一块纯色方块」：同一个挖空问题，这次栽在**应用图标 `.icns`** 上。
  列表拿不到模式图标时会回退到 app 图标，而它**同样按模板图渲染** → 实心的 `.icns` 被涂成一整块。
  已把 `.icns` 也改成挖空（与鼠须管的 `RimeIcon.icns` 一致），见 下文「故障排查」
- **0.4.2** —— 两件事：
  ①「查编码拼音只出一两个字」：码表里同音字**各带形码**（好=hc、号=hck、浩=hcd、豪=hcw），
  原来按**精确匹配**查 `hc` 只回得来「好」一个字。改成**前缀匹配**并列出同音一整族
  （候选窗 3 行 × 9 列网格 + 自动翻页，上限 256），拼音、双拼、中途态都能查。
  ②「切换菜单里图标比别人的小」：实测我们渲染成 **26×26 px 小方块**（`.icns` 兜底），
  而 ABC / 鼠须管 / 简体拼音都是 **44×32 px** —— 但那是**设置列表的固定槽位**在缩放源图，
  鼠须管只有 16×16 的 `rime.pdf`，在列表里照样是 44×32。**列表的值不能拿来推断菜单栏**，
  详见下文「菜单栏图标」一节。
  TIS 本身能解析到我们的 PDF（`IconImageURL` 指向 `SimpleFly.pdf`），差异出在 plist：
  删掉 Tiger 时代的顶层 `tsInputMethodIconFileKey`（鼠须管没有它），补上 `CFBundleIconName`。见 下文「故障排查」
- **0.4.3** —— 「查编码」从「查一个字就退」改成**常驻拼音输入法**，对应用户场景
  「不会按小鹤音形拆字，切拼音输入法把字打出来、直接看编码」：
  ① `ReverseModeAutoExit` 默认 **YES→NO**，`Ctrl+/` 进入后一直保持拼音模式，可连续打拼音出字（像普通拼音输入法），按 Esc / 再按 `Ctrl+/` 才退；
  ②上屏后 HUD 短暂显示该字音形码（「好  hc·nz」，1.8s），直接满足「打出来后看编码」。
  引擎层 `hao`→`hc`→26 候选、控制器 `test_reverse_mode` 均正常，0.4.2 已装好，所以这次是交互模型问题不是旧版本 bug。
- **0.4.4** —— 「查编码」支持**词语查询**，对应「用拼音查整词、直接看整词编码」的场景：
  ① 多音节拼音也能查（`nihao` → `nihc` → `你好`），新增 `sf_pinyin_to_double_multi` 把拼音按音节切开逐个转双拼码再拼起来；
  ② 同前缀下**单字 + 词语都列**：单字排前、词语排后（好 / 号 … 之后跟 好啊 / 好吧），`sf_engine_lookup_prefix` 的 `singles_only` 改成三态（0 都要 / 1 只要单字 / 2 只要词语）。
- **0.5.0** —— **候选窗配色主题化**：写死的配色宏抽成 `SFCandidateTheme` 运行时对象，
  内置 `metro`（浅，原配色）/ `dark`（深灰底靛蓝高亮）/ `paper`（暖白纸底橙高亮）；
  `Ctrl+;` 循环切换（写回 `Theme` 偏好，未知名兜底 metro），切换不清组字状态、正组字时即时重绘；
  加主题 = `SFCandidateTheme.m` 的 `kThemes` 表加一行 10 色值；`./build.sh --preview` 离线渲染三主题拼图（`docs/主题预览.png`），不用注销重登就能看效果。
- **0.5.1** —— 「系统设置列表里图标比别人的小」（**真机已验证修好**）：
  截图实测我们渲染成 **26×26 px 小方块**，像素级比对确认它就是 `.icns` 的 `icon_16x16@2x` 帧 ——
  即列表**压根没在用模式图标**，一直在回退 app 图标。而 plist 三键、PDF、TIS 的 `iconURL` 全都正确，
  重新注册也没用 —— 说明 **macOS 26 的设置列表不采用 22×16 的 PDF 模式图标**。
  正解照抄 Apple：解剖 SCIM.app 的 `pinyin.tiff`（列表里显示正常的「拼」徽标）得到规格 =
  **双帧 TIFF（16×16@72dpi + 32×32@144dpi）、黑墨 + alpha 模板、满幅圆角底板 + 挖空字形**，
  照此生成 `SimpleFly.tiff`，三个 `tsInputMode*IconFileKey` 全指向它。
  **根因与旧结论的差异**：0.4.2 那次是 plist 顶层键导致回退；这次是**文件格式不被列表接受** ——
  PDF 在菜单栏能用，不代表设置列表会用。见 下文「故障排查」
- **0.6.0** —— **缺码表时给可见提示**（开源准备的一部分）：本仓库不含码表，clone 之后没放码表
  就按任何键都毫无反应，而原来只有一行 NSLog —— 最容易被误判成「装坏了」。现在弹 HUD 指名放到
  哪个目录，并且**不吞键**（字母照常上屏，至少还能当英文键盘用）。
  同时 `./build.sh --test` 在无码表时不再崩在第 6 套：依赖码表的套件明确跳过，缺表时还会清掉
  `build/` 里残留的旧表（留着会让测试以为有表，缺表分支永远测不到）。
- **0.7.0**（build 30）—— **菜单一键自更新**（本仓库第一个走 GitHub Release 分发的版本）：
  输入法菜单顶项「更新到最新版本」，点一下由 `tools/self_update.sh` 在**独立进程**里跑完
  拉取 → 构建 → 安装 → 免登刷新。**双模式自动选择**：本机有源码仓库就走源码模式
  （`git fetch` + `merge --ff-only` + `build.sh` + `install.sh`）；没有就走预编译模式
  （下载 Release 的 `SimpleFly.app.zip` 解压替换，**只需系统自带 `curl`，不需要 git / Xcode CLT**）。
  三个关键设计：① 更新器是**独立进程**，`install.sh` 末尾的 `pkill -x SimpleFly` 带不走它；
  ② 脚本启动先自拷贝到 `/tmp` 再 `exec`，否则 `install.sh` 的 `rm -rf "$DEST"` 会把**正在执行的自己**删掉、
  读到一半 EOF 中断；③ 更新前只做时间戳备份，**绝不删除** `Application Support` 与 `defaults`。
  配套 `tools/package_release.sh` 出包（构建 → 内嵌 `tis_register` → 打成 `SimpleFly.app.zip`）。
- **0.7.1**（build 31）—— **菜单文案精简**：标题里的括号补充全部拿掉
  （「更新到最新版（拉取并构建）」→「更新到最新版本」、「同步到网盘（短语·重码记忆）」→「同步到网盘」、
  「候选窗编码提示 开 ✓（⌃⇧H）」→ 去掉快捷键后缀），细节收进《用户手册》§四「输入法菜单一览」表。
  顺带修掉 `controller_test` 里一条**从 0.7.0 起就红**的陈旧菜单断言（它还断言「菜单 4 项」，实际已 6 项）；
  新断言把「标题精确匹配 + 标题不含括号」固化下来。
- **0.7.2**（build 32）—— **修掉「签名无效」**：`codesign -v` 一直报
  `invalid resource directory` / `a sealed resource is missing or invalid`，三个脚本各有一半责任。
  ① `package_release.sh` 在 `build.sh` 签完名**之后**才把 `tis_register` 嵌进 `Contents/Resources`，
  不对应更新资源封条 —— 于是 **0.7.0 与 0.7.1 两版线上 asset 都是签名无效的包**；
  ② `install.sh` 直接 `cp -R` 到 `~/Library/Input Methods/SimpleFly.app` 再**原地** `codesign`，
  而 TIS 只要发现这个输入法被选中（系统记住的选择不因 `pkill` 消失）就会立刻把刚落地的 bundle
  拉起来执行，`codesign` 偏偏是「主二进制拷成 `xxx.cstemp` → 改 → 挪回」的原地操作，
  对着正在执行的 bundle 签名，封条必然对不上（对照实验：同一份 app 复制到 `/tmp` 再签 → `valid on disk`）；
  ③ `self_update.sh` 预编译模式把解压出的 app 直接 `cp -R` 进目标位置，既不校验也不补签，
  会把无效签名原样继承，老用户更新即中招。
  改法统一为「**先签好、验过，再 `rename` 换上去**」：`package_release.sh` 嵌完重签并复核 zip 内容；
  `install.sh` 暂存目录签名 → 校验 → 替换；`self_update.sh` 落地前校验签名、无效则补签。
  顺带记一个自己踩的坑：`codesign --verify … | grep -q` 在 `set -o pipefail` 下，
  `grep -q` 命中即退出会让 codesign 吃 SIGPIPE 而非零退出，把「签名有效」误判成失败 ——
  判据一律改用 codesign 自己的退出码。
- **0.7.3**（build 33）—— **菜单栏图标不再比别人窄**：菜单栏读的是顶层
  `tsInputMethodIconFileKey` + 两个 mode 级菜单图标键，0.5.1 为修设置列表把这两个 mode 键
  **也**指向了 16×16 方形 TIFF、还删掉了顶层键，于是菜单栏图标退回 16×16
  （系统「简体拼音」的「拼」是 22×16 pt —— 实测 44×31 px）。改回三键同指 22×16 pt 的 `SimpleFly.pdf`，
  `tsInputModePaletteIconFileKey` 仍留给 TIFF —— **两个文件分工，别混**。
  顺带查清「菜单栏为什么带名字」：那是 macOS 的全局显示项（**输入法菜单里的「隐藏输入法名称」**），
  不是本输入法的开关。两条排查经过见 下文「菜单栏图标 / 名称」。
  另记一个卡人的坑：**TIS 按「文件路径」缓存图标**，同路径改内容不生效，只有注销重登或换文件名
  （0.7.3 本机就是靠**换名实验**当场验证的：32×32 px → 44×31 px）。
- **0.7.4**（build 34）—— **菜单加「用户配置」**：一行打开配置目录
  （`~/Library/Application Support/SimpleFly/`，用访达打开），`phrase.txt`（自定义短语）、
  `simplefly.dict`（用户码表）、`webdav.conf`（网盘）一次看全 —— 不再逐个文件配菜单项
  （那样菜单会越拉越长，用户还得先知道有这么些文件）。
  首次点（目录或 `phrase.txt` 还不存在）先补一份带说明的示例，否则打开的是**空目录**，
  用户不知道该建什么文件、里面写什么；示例只在文件缺席时写，**已有内容绝不覆盖**（单测锁死）。
  配套加 `SIMPLEFLY_USER_CONFIG_DIR` 环境变量可把目录指到别处：离线单测靠它把动作限制在临时目录，
  既不会碰用户真实配置、也不在测试机上弹访达；`controller_test` 的菜单断言同步改成八项。
  同一版还加了 **「快捷键一览」子菜单**：把《用户手册》§四 的 12 条键位原样搬进菜单，
  以后忘组合键不用翻文档。两个刻意的取舍：① 键位**不走 `keyEquivalent`**（那是「菜单项绑定了键」、
  会真的参与按键匹配），而是作为**文本**写进标题、按显示宽度补空格对齐；
  ② 每一行都**不带 action**（系统自动置灰、点不动）—— 一览里躺着「清空重码记忆」这种破坏性动作
  和「先选中文字再按」这种条件动作，做成可点只会带来误触与「点了没反应」的困惑。
  单测把「15 项 = 12 键位 + 3 分隔线」「每行无 action/target」「键位文本与手册逐字一致」都锁住了。
  收尾又做两件事：① **菜单标题一律去掉省略号** —— `从网盘恢复…` / `网盘配置…` / `用户配置…` 都改成
  无后缀。理由不是「难看」而是语义：`…` 在 macOS 上的约定是「点完还得再填一步才能完成」（弹对话框），
  而这几项都是点一下就做完（开目录、开配置文件、开手册），缀上省略号反而像没做完。
  ② 菜单末尾加 **「用户手册」**，打开随 app 内嵌的 `Contents/Resources/用户手册.md` ——
  **普通用户装的是 Release 的 zip，机器上没有源码仓库**，手册不随包走就等于没有。
  `build.sh` 负责把仓库根的手册拷进 bundle；`install.sh` 的「二进制新鲜度自检」把 `用户手册.md`
  也算进过期判据（改了手册没重构建 = 菜单打开的还是旧版正文，比「改了代码没 build」更难察觉）。
  打开方式用系统给 `.md` 注册的默认应用（装了 Typora / Obsidian 就是它），
  `openFile:` 返回 NO（全新系统常见：`.md` 无人认领）再退回「文本编辑」。
  路径解析仿 `s2t.tsv` 那套：环境变量 `SIMPLEFLY_USER_MANUAL`（离线单测）→ bundle 资源 → 可执行文件旁。
  菜单断言随之改成九项，并新增「**任何项标题都不缀省略号**」和 `test_user_manual()`（路径解析 ×3 场景）。
- **0.8.0**（build 35；**b36 / b38 / b39 三次修「菜单里选主题点了没反应」，b41 把主题入口收成二级菜单**）—— **候选窗皮肤扩到 13 款，加菜单选款与「跟随系统亮暗」**：
  ① **配色**：新增 `jade`（青玉，雾青底青玉绿，低饱和护眼）/ `blossom`（桃夭，暖粉底玫红）/
  `linen`（亚麻，中性暖白配深灰蓝，几乎无色相干扰）/ `contrast`（纯黑白，对比度 21:1，视力障碍与投屏用）
  四款浅色，`amber`（琥珀，色相整体压在橙黄区、**蓝光最少**，睡前用）/ `neon`（霓虹，近黑底高饱和青绿）/
  `retro`（终端，近黑底磷光绿）三款深色；同时**下掉 `aqua` 与 `google`** —— 连原有的 `metro` 在内，
  这三款都是「浅底 + 蓝高亮」，辨识度几乎为零，主题一多反而挑花眼。数组顺序按「日用 → 夜用」排，
  `Ctrl+;` 循环一圈有昼夜过渡感，而不是浅深浅深来回跳。老配置里若还写着被下掉的名字，
  `themeNamed` 回退 `metro`（控制器另有一道 `allThemeNames` 校验兜着），不会拿到空配色而崩在绘制里。
  ② **菜单选款**：主菜单只留一条「选择主题…」，点它弹出第二层菜单（13 款 + 当前款打勾 +
  分隔线 + 「跟随系统亮暗」）。这条路径**连踩三次**，三次症状都是「点菜单项完全没反应」——
  不报错、不崩溃、项也不变灰，根子都在「菜单命令究竟怎么回到 controller 手上」这个机制上
  （前两次是**认领方式**错，第三次**连命令都没回来** —— 方向完全不同，见下面 b38）：
    · **初版**：按「IMK 只拦发往 controller 的命令、发给自定义 target 的动作直连」这个推断，
      给每项挂了自带主题名的轻量 target（`SFThemePicker`）。**推断正好反了** —— 系统走
      `-doCommandBySelector:commandDictionary:`（`IMKInputController` 的默认实现），它只检查
      **input controller 自己**的 `respondsToSelector:`，响应就把 `infoDictionary` 当参数发过去，
      **根本不看菜单项上的 target** —— 挂在别的对象上的 action 永远收不到。
      而「拿不到被点的 `NSMenuItem`」同样是误判：那份字典里 `kIMKCommandMenuItemName`
      就是被点选的那个 `NSMenuItem`（`IMKInputController.h` 写明）。
    · **b35**：改成各项共用 controller 上的 `menuThemePick:`、从 `representedObject` / 标题认领主题名。
      **真机上依然毫无反应** —— 因为**派发形态不止一种**：除了上面那条 IMK 转发（sender 是字典），
      AppKit 也可能按常规菜单行为直接把 action 发给 target（= controller），此时 sender 是
      `NSMenuItem` 本身。b35 只处理了字典形态，遇到第二种就解析不出主题名、提前 return；
      而它那条兜底 HUD 又把 `NSMenuItem` 当 client 传下去，`candidateTopLeftWithClient:` 的
      `respondsToSelector:` 保护让它退化成「跟着鼠标走」—— 点菜单时鼠标正停在屏幕顶端，
      提示等于看不见，所以连报错都没有。
    · **b37 的改法**：不再猜形态 —— **每款主题一个独立 selector（`menuTheme_<主题名>:`），
      主题名直接编进方法名**。无论走哪条派发路径、sender 里装着什么，方法名本身就是凭据，
      不依赖任何运行时对象。client 另走三路兜底（字典里 `kIMKCommandClientName` → sender 本身
      若是 client → controller 自己的 `-client`），**绝不再把菜单项当 client**。
      增删主题时 `SFCandidateTheme` 的 `kThemes` 与那批 `SF_THEME_ACTION` 要一起改：
      只加主题、忘了加方法，那一款就是「点了没反应」。单测有断言逐款校验 selector 名与
      `respondsToSelector:`，漏了当场挂。排查期另加了一条诊断日志
      `~/Library/Application Support/SimpleFly/menu-debug.log`（记 selector、sender 类名、
      解析出的主题名；上限 32 KB；`defaults write … MenuDebug -bool NO` 可关），
      它会直接说明真机走的是哪种形态。
    · **b38 的改法 —— 方向翻面**：换成独立 selector 后**真机依然点了没反应**，而那份诊断日志
      **一行都没写**。这片空白恰好排掉了前两轮的死因：命令不是「回来了但没认出来」，而是
      **压根没回来**。于是不再查「怎么认领」，改查「点击为什么到不了我们」。最像的物理原因是
      **菜单项被系统判成不可用（置灰）** —— 菜单有可能被送到**菜单栏代理进程**去显示，那边
      既没有我们的 controller，也读不到 `target`（`NSMenuItem.target` 是 **weak 且不参与
      归档**，跨进程后是 nil），按常规判定就成了「没有对象响应这个 action」；**置灰的项点了
      不产生任何回调**，所以日志必然是空的 —— 这与观察到的现象完全吻合。三条防线一起上：
      ① `menu.autoenablesItems = NO`，不让系统替我们做可用性判定（代价：纯文本行得自己
      显式置灰，见 `SFAddKeyRow()`）；② 自己实现 `-validateMenuItem:` 回答可用性；
      ③ 自己实现 `-doCommandBySelector:commandDictionary:` 掌住派发路径，并把每条经过的命令
      记进日志。这样「菜单没被取走」「点击没回来」「回来了没认出来」三种情形各有各的日志，
      下一轮不用再猜。
    · **b39 的改法 —— 病根在「子菜单」**：b38 的诊断日志交出了决定性证据 —— 用户连开 11 次
      菜单，日志里**只有** `menu built items=10`（系统确实每次都在取我们的菜单），而
      `validate` / `IMK cmd` / `theme pick` **一条都没有** ⇒ 点击没产生任何回调。
      同时用 `screencapture -x -R` 抓到了菜单展开时的实拍（**这一招以后还要用**：没有辅助功能
      权限也能拿到界面证据）：**主题项根本不是灰的** —— 与可点的「用户手册」同色、`✓` 也正确
      打在当前款 `paper` 上 ⇒「项被系统判成置灰」这条不成立。两条证据合起来只剩一个解释：
      **放进子菜单的项没有被接上派发**（顶层项走一套、子菜单项走另一套）。旁证：本机装着的
      鼠须管（0.15.2，能正常工作）`-menu` 里**一个子菜单都没有**，动作全是顶层静态 selector；
      拉它现在的 Swift 源码（`sources/SquirrelInputController.swift`）也是 `target = self` +
      静态 selector、无 submenu、不重写 `doCommandBySelector` —— 与我们「挂法」一致。
      **改法：13 款主题 + 「跟随系统亮暗」平铺进主菜单**（标题加「主题：」前缀自解释），
      只用分隔线与上面的动作项隔开。菜单从 10 项变 24 项，比好看更重要的是点得动。
      保留的子菜单只剩「快捷键一览」—— 那里全是只读说明，本来就不需要派发。
    · **「子菜单为什么点不动」翻头文件找到了机制依据。** 日后要复盘的直接看这段：
      `IMKInputController.h`（`/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/System/Library/
      Frameworks/InputMethodKit.framework/Headers/`，282~296 行）写明两点 —— ① 菜单是画在**系统的
      Text Input Menu** 里的（原文 "when a user selects a command item from **the text input menu**"），
      不是我们的进程画的 ⇒ `target` 跨进程必然失效（`NSMenuItem.target` 是 weak、不参与归档）；
      ② 默认派发是 `performSelector:withObject:(infoDictionary)` —— **IMK 自己遍历菜单按 selector 建
      命令表，而「遍历」只走顶层项、不进子菜单** ⇒ 子菜单叶子的 action 压根没进那张表，点击连
      `-doCommandBySelector:` 都不会进。
      **这个失败模式特别坑：子菜单叶子能正常渲染、能正确打勾、也不置灰，只是点下去静默无声** ——
      b37 误判成「命令回来了但没认领」、b38 误判成「项被判成置灰」，都源于此。
      二进制旁证（同一手法先在鼠须管上验了有效性）：`LC_ALL=C grep -a -o -c 'setSubmenu:'` 对
      鼠须管 0.15.2 主二进制 = **0**，而同法 `'deploy:'` / `'syncUserData:'` 各 4 命中 ⇒
      **能正常工作的同行一个子菜单都不用**，不是我们挂错了。
      ⇒ **「折叠的二级」改由我们自己 popUp（b41 落地）**：主菜单只留一条顶层项「选择主题…」
      （顶层派发已验证可靠），在它的 action 里 `popUpMenuPositioningItem:atLocation:inView:`
      弹出**我们自己建的** NSMenu —— 这张菜单由 AppKit 在本进程内按 target-action 派发、`target`
      有效，二级选择才可靠。代价是「点一下才展开」，不是悬停级联。
    · **b41 落地细节（几处只有踩过才知道的）**：
      · 菜单从 24 项缩到 **11 项** —— 「选择主题…」一条顶掉原来 14 项（13 款 + 「跟随系统亮暗」，
        末项前的分隔线保留）。主题组不再需要「主题：」前缀。
      · 第二层菜单**布局**：置灰小标题「候选窗配色」+ 13 款（标题就是主题名）+ 分隔线 +
        「跟随系统亮暗」，共 16 项。**不缀「主题：」前缀** —— 那是平铺进主菜单时的语境补偿
        （一列 metro / jade 混在 24 项里不知道是什么），在专供选主题的菜单里再缀一遍就是 13 行重复。
      · `popUpMenuPositioningItem:atLocation:inView:` **返回 BOOL（有没有选中某一项），不是选中项**。
        第一版按「返回值就是选中项」写了兜底路径，编译才发现类型不对（ARC 报
        `implicit conversion of 'BOOL' … to 'NSMenuItem *' is disallowed`）—— 选中了哪一项只能靠
        action 派发拿到。于是把兜底改成**探针**：日志记 `theme picker closed selected=N handled=M`，
        只有 `selected=1 handled=0`（用户选了、action 却没派出去）才需要补兜底，届时再补。
      · 菜单位置取 `[NSEvent mouseLocation]`：指针就在刚点的「选择主题…」上，于是第二层在指针处
        展开，视觉上就是一次正常的级联。`inView:` 传 nil ⇒ `atLocation:` 走**屏幕坐标**，与
        `mouseLocation` 同一套原点约定；贴近屏幕顶端时 AppKit 自己会把菜单夹回屏幕内。
      · **`popUpThemeMenu` 绝不能进单测** —— 它会真的弹菜单并原地等用户操作，一调就卡死。
        所以留了一层壳 `themePickerMenu`（只造菜单、不弹），单测拿它逐项断言；测试文件里也
        刻意**不声明** `popUpThemeMenu`，从类型层面挡住误调。
      · 单测项数 744 → **727** —— **不是漏测**：主菜单 24 → 11 项，而那条「逐项断言标题不含括号 /
        不缀省略号」的循环每个菜单项贡献 2 条断言，自然少掉 26 条。
      · 「不缀省略号」的规矩**开了唯一一个例外**：「选择主题…」点完确实还要再选一层，缀上才符合
        预期。测试改成「逐项断言不缀 + 单独断言这一项必须缀」，将来谁把入口改成「点一下就完事」
        （比如改成循环切下一款）会当场挂，提醒同步改文案与手册。
  ③ **`ThemeAuto`（默认关）**：浅色系统用 `jade`、深色用 `amber`，监听 `AppleInterfaceThemeChangedNotification`
  实时切。两条刻意定的规则：跟随期间**不写回** `Theme` —— 那是用户手选的，关掉跟随就该回到它；
  手动选款（菜单里点，或 `Ctrl+;`）**自动退出跟随**，否则刚选的那款会被下一次外观变化覆盖，
  在用户看来就是「选了没用」。外观判断走 `NSApp.effectiveAppearance`，拿不到有效外观时退回
  `AppleInterfaceStyle` 全局偏好；单测没法改系统外观，用 `SIMPLEFLY_FORCE_DARK`（0 / 1）指定。
  ④ **单测 609 → 744 项（b41 收成二级菜单后为 727，原因见上）**：主题清单、各款色相方向（jade 绿最大 / blossom 红最大 / amber 蓝最小…）、
  半透明只属于 `luna` 与 `ink`，逐条断言；另加两条**通用防呆** —— 底色与候选字的感知亮度差须 > 0.25，
  高亮块内词 > 0.25、编号与附注 > 0.15。这两条阈值是补出来的：第一版出 `--preview` 预览图时肉眼发现
  `neon` / `retro` 的附注（亮青 / 浅绿）压在青绿 / 磷光绿高亮块上几乎看不见（Δ 仅 0.09）——
  **色值摊开看没问题、渲染出来才发现**，这类只有出图能抓。菜单断言随之改成十项，
  并新增「主题」子菜单的结构断言（15 项 = 13 款 + 分隔线 + 跟随项；每项 selector 严格等于
  `menuTheme_<主题名>:` 且互不相同、controller 真的响应；当前款打勾；跟随时主题列一个都不打勾）。
  **最关键的是两条「真派发」断言**，分别覆盖两种派发形态：① 字典形态 —— 直接调
  `-doCommandBySelector:commandDictionary:`（IMK 转发就是这么派的）；② 菜单项直调形态 ——
  用 `methodForSelector` 取 IMP 后按 `(id, SEL, id)` 调用（AppKit 直接发 action 就是这么走的），
  断言主题真的切过去。b35 之所以漏网，就是**只测了结构、只覆盖了其中一条路径**。
  b38 再补 7 条**菜单可用性**断言：顶层菜单与「主题」子菜单的 `autoenablesItems` 必须为 NO、
  `-doCommandBySelector:commandDictionary:` 的 IMP 必须是我们自己那份、`-validateMenuItem:`
  对主题动作放行而对响应不了的动作挡住、「快捷键一览」每行都是无 action 的置灰文本。
  **教训**：结构断言全绿不代表路径能走通；而「菜单根本没被取走 / 项被判成置灰」这类故障，
  连派发断言都测不到 —— 真机上只有日志能说话，所以诊断日志要留在代码里、别急着删。
  b39 把主题组从子菜单改成主菜单平铺，菜单断言随之改成 **24 项**：主题 13 项按 `10 + i`
  的下标逐项校验（标题 = `主题：<名>`、selector = `menuTheme_<名>:` 且互不相同、
  `representedObject` 带主题名、target 是 controller）；b38 那批**可用性断言原样保留** ——
  「项被判成置灰」这次不是病根，但换台机器/换个系统版本仍可能是，拆掉就等于把门敞开。
  ⑤ **b41 收成二级菜单**：主菜单断言改成 **11 项**（末项 =「选择主题…」，并断言它**不带 submenu** ——
  把「不许走回 IMK 子菜单」这条设计决定也锁进测试）；主题那批断言整体搬到第二层，改用
  `themePickerMenu` 造出菜单后逐项校验（16 项 = 小标题 + 13 款 + 分隔线 + 跟随；13 款标题就是
  主题名、都必须是可点的、selector 严格对应、`representedObject` 带名字）。

### `controller_test` 是怎么在没有输入法会话的情况下跑起来的

输入法在真机上只能靠「手打一遍看效果」验证，某个分支写错的表现是「某个键没反应」，极难定位。
这一套把 `SimpleFlyInputController` 装上一个假客户端直接喂合成的 `NSEvent`，断言「最终上屏了什么」。
两个关键手法：

1. **覆盖 `-updateComposition` 成空操作**。`IMKInputController` 的这个方法要和真实输入法会话通信；
   覆盖掉之后整条链路（`handleEvent:` → 状态机 → 上屏）完全不依赖 IMK 运行时，普通命令行程序就能跑。
2. **事件用 `+[NSEvent keyEventWithType:…]` 自己造**，`characters` / `keyCode` / `modifierFlags`
   全部由测试指定，所以不需要真实键盘 —— 连「单敲 Shift」这种只在 `flagsChanged` 里出现的操作也能测。

另外它是**运行时找真实编码**（`FindCode()`）而不是把编码写死：曾经写死过 `hao`，结果码表里根本没有
这个编码（小鹤双拼里 `ao` 映射到 `c`，好 = `hc`），测试假失败了一次。

跑之前会暂存并清空本机的输入法偏好，结束时还原 —— 免得「跑个测试把用户的中英标点设置改了」。

## 故障排查：「装好了，但系统设置里看不到」

这个症状有**两个层次**，先分清在哪一层，否则会一直修错地方：

| 层次 | 现象 | 判据 |
|---|---|---|
| **A. TIS 压根不认这个 bundle** | 系统设置里找不到，切也切不过去 | TIS 枚举（含未安装）里**查不到**这个 bundle |
| **B. TIS 认了、也能用，但列表里认不出** | 系统设置里其实有它，只是名字显示成一串 `com.xxx.inputmethod.Yyy.Hans` | TIS 枚举**查得到**，但 `localizedName` 等于输入源 ID 本身 |

### A 层：三条硬性要求，缺任何一条 TIS 都**静默忽略整个 bundle**

不报错、不写日志、`--check` 一切正常，所以很容易误判成「没生效」。

| # | 硬性要求 | 0.1.0 的情况 |
|---|---|---|
| 1 | 输入模式必须用 **`ComponentInputModeDict`** 声明（Apple TN2128：「Your Info.plist **must** specify the "ComponentInputModeDict" key … even for non-component application-based input methods」）。只在顶层放 `tsInputMethodCharacterRepertoireKey` 是 Tiger 时代的老写法，macOS 15 不再识别 | ❌ 只有老写法 |
| 2 | `CFBundleIdentifier` 必须是 **`<厂商>.inputmethod.<产品>`** 三段式，字面含 `.inputmethod.`（带尾点）—— TIS 构造 InputSourceID 靠「删掉以 `.inputmethod.` 结尾的前缀」 | ❌ 是 `com.simplefly.inputmethod`，缺产品段 |

参照物：系统上能用的输入法全是这个形状 —— `com.apple.inputmethod.SCIM`、`com.apple.inputmethod.Kotoeri`、`im.rime.inputmethod.Squirrel`。

### B 层：`InfoPlist.strings` 的 key 必须是**完整输入源 ID**

0.2.0 就是这个症状 —— 它其实已经能用了，只是在列表里名字不对。

TIS 取显示名时用的 key **就是输入源 ID**（= bundle id + 模式后缀），不是 `CFBundleName`：

```
/* en.lproj/InfoPlist.strings —— 正确写法 */
CFBundleName = "SimpleFly";
"com.simplefly.inputmethod.SimpleFly"      = "SimpleFly";
"com.simplefly.inputmethod.SimpleFly.Hans" = "SimpleFly - Flypy";
```

对照鼠须管的 `zh-Hans.lproj/InfoPlist.strings`，形状完全一样：

```
"im.rime.inputmethod.Squirrel"      = "鼠须管";
"im.rime.inputmethod.Squirrel.Hans" = "鼠须管";
```

**0.2.0 的 bug 是 key 只写了 `com.simplefly.inputmethod.Hans`** —— 上一轮把 bundle id 从两段改成三段时，`.SimpleFly` 那一段忘了同步进去。key 匹配不上，系统就 fallback 把输入源 ID 原样当名字：

```
localizedName  = com.simplefly.inputmethod.SimpleFly.Hans   ← 用户看到这串，认不出是 SimpleFly
```

**教训**：改 `CFBundleIdentifier` 时要同步三处 —— `Info.plist` 里的 `TISInputSourceID` / `tsInputModeListKey` 的 key、`InfoPlist.strings` 里的 key、以及 README 里 `defaults` 的域。

### 怎么自己确认（不注销）

`log show` 在沙箱里跑不了，TIS 也没有命令行工具 —— 用 `tools/` 里这三个：

```bash
for t in inputsource_list tis_register tis_diag; do
  clang -O2 -isysroot "$(xcrun --show-sdk-path)" "tools/$t.c" -o "/tmp/$t" -framework Carbon
done
```

| 工具 | 回答什么问题 |
|---|---|
| `inputsource_list.c` | **TIS 认不认这个 bundle**（认了没认是两个完全不同的修法） |
| `preview_sheet.m` / `tile.m` | **图标会不会被系统涂成一整块** —— 按模板图规则（`涂色×alpha + 背景×(1-alpha)`）自己算每个像素，把彩色 / 浅色 / 深色 / 实际大小四列并排；不依赖真机就能判断有效性 |
| `tis_diag.c` | **认了之后状态对不对** —— 输出 `localizedName`（显示名）、`invisible`、`enableCapable`、`selectCapable`、`iconURL`，还能 `--select` 当场切过去 |
| `tis_register.c` | 调 `TISRegisterInputSource()` 当场注册；返回 0 且随后能枚举到 = plist 合法 |

```bash
/tmp/inputsource_list --all simplefly         # 认不认
/tmp/tis_diag simplefly                       # 状态全貌（对照 /tmp/tis_diag Squirrel）
/tmp/tis_register "/path/to/SimpleFly.app"    # 当场重新注册（改完 plist 用）
```

`tis_diag` 的输出怎么读 —— 和能用的鼠须管逐项对齐，**任何一项不同就是病灶**：

| 字段 | 正常值 | 不对时意味着 |
|---|---|---|
| `localizedName` | 人读的名字（如 `SimpleFly - Flypy`） | **等于输入源 ID** → `InfoPlist.strings` 的 key 写错了（B 层） |
| `invisible` | `0` | `1` → 系统设置里永远看不到 |
| `enableCapable` / `selectCapable` | `1` / `1` | `0` → 加不进列表 / 切不过去 |
| `languages` | `zh-Hans` | 空 → 不会被归到任何语言分类，那个 `+` 列表里就翻不到 |
| `enabled` | `1` | `0` → 得先 `tisreg … --enable` |

> 判定口径别搞混：`TISCreateInputSourceList(NULL, true)` 是「所有已安装」（含未启用），`(NULL, false)` 才是「用户已添加的」，也就是系统设置里那个列表。
> 另外输入法本体是 `TISTypeKeyboardInputMethodModeEnabled`，模式级是 `TISTypeKeyboardInputMode` —— 用 `"KeyboardInputMode"` 子串区分，用 `"InputMethodMode"` 会误判。

### 能不能不注销？

**B 层的问题（显示名之类）不用注销**：改 → `build.sh` → `install.sh` → `tis_register` 重新注册，`tis_diag` 里 `localizedName` 会立刻变。实测有效。

**要不要注销才能首次添加**：`TISRegisterInputSource` 的注册效果**是持久的**（实测：注册后注销重登，TIS 依然枚举得到该 bundle，不依赖当次会话）。macOS 13+ 首次添加第三方输入法还会弹「**TextInputMenuAgent 想启用第三方输入法**」，**必须点允许**。粤拼、鼠须管的官方安装说明都写注销重登 —— 稳一点就走这一步。

**想完全跳过注销**：`tis_diag … --select` 调 `TISSelectInputSource()` 直接把它切成当前输入法，实测返回 0 并立即生效（`AppleSelectedInputSources` 里就换成了它）。适合自用验证。

### 图标：为什么必须「挖空」（0.3.1）

**症状**：系统里显示的是一整块纯黑的圆角方块，「鹤」完全看不见。

**根因**：输入法在**菜单栏 / 输入源列表**里的图标是**模板图**——系统只看 alpha 通道，
颜色由系统自己涂成单色（浅色模式黑、深色模式白）。于是：

| 画法 | alpha 结构 | 渲染结果 |
|---|---|---|
| 不透明底 + **不透明**白字（0.3.0 及以前） | 整块都是 255 | **一整块纯黑（或纯白）方块**，字消失 |
| 不透明底 + **挖空**的字形（0.3.1） | 底 255、字形 0 | 黑底透出背景色的字 ✔ |

「黑底挖出字形」正是系统输入法的标准画法：macOS 日本语输入法菜单栏那个「あ」就是

底色区域 `alpha=255`，就是个挖空；而 0.3.0 的 `SimpleFly.pdf` 中心 `alpha=255`，所以被涂成一整块。

### 图标尺寸：为什么切换菜单里比别人小（0.4.2）

**症状**：0.4.1 挖空修完后图标能显示了，但在**输入法切换菜单**（`Ctrl+空格` 或点菜单栏输入菜单
弹出的那个列表）里，我们的徽标明显比别人的小。

**逐像素实测**（对用户截图跑连通域分析，@2x 屏）：

| 行 | 徽标实测 | 换算 | 来源 |
|---|---|---|---|
| ABC / 鼠须管 / 简体拼音 | 44×32 px | 列表槽位满尺寸 | **设置列表**的固定槽位会缩放源图（鼠须管 `rime.pdf` 实测只有 16×16 pt）—— **不能拿它反推菜单栏** |
| 小鹤音形（0.4.1） | **26×26 px** | 13×13 pt | **`.icns` 兜底**：16 pt 槽位 × 内容占比 0.804（应用图标网格 824/1024）≈ 12.9 pt |

26×26 这个数能精确反推出系统在用哪个文件 —— 它不是 22×16 PDF 缩放的任何可能结果
（PDF 等比缩放进方形槽只会得到 44×32 或更扁），只能是方形的 `.icns`。

**排除了什么**（都是实测，不是猜）：

- PDF 本身没问题：页面 22×16 pt、不透明内容横跨整页（鼠须管 `rime.pdf` 结构相同但页面只有 16×16 pt，
  覆盖率 62.7% vs 81.3% 的差别只在字形笔画多少，不影响槽位尺寸）；
- TIS 能解析到模式 PDF：`TISGetInputSourceProperty(kTISPropertyIconImageURL)`
  返回 `…/SimpleFly.app/Contents/Resources/SimpleFly.pdf`（鼠须管同型返回自己的 `rime.pdf`；
  `kTISPropertyIconRef` 两者都是 NULL —— 系统输入法 ABC 才走老的 IconRef 路，IMK 都走 URL）；
- 不是沙箱：System Settings 没有 `com.apple.security.app-sandbox` 授权。

**剩下的差异就在 plist**：我们多了一个 Tiger 时代的顶层 `tsInputMethodIconFileKey`
（鼠须管没有），且缺现代的 `CFBundleIconName`（鼠须管有）。0.4.2 把这两处对齐。

**注销重登后如果还是 26×26 小方块**，按顺序试：

1. `killall TextInputMenuAgent SystemUIServer` 后再看切换菜单（不用注销）；
2. 确认装的是最新版：
   `plutil -extract CFBundleVersion raw ~/Library/Input\ Methods/SimpleFly.app/Contents/Info.plist` → 0.5.1 应为 `11`；
3. 终极手段 —— 装到系统目录（需 sudo，鼠须管就在那里）：
   `sudo cp -R build/SimpleFly.app "/Library/Input Methods/"`。
   `/Library` 下的 bundle 由 root 持有，系统代理进程读它没有任何歧义；
   卸载用 `sudo rm -rf "/Library/Input Methods/SimpleFly.app"`。

### 模式图标：为什么设置列表里比别人小（0.5.1 · 真机已验证修好）

**症状**：0.4.2 之后菜单栏没问题，但「**系统设置 › 键盘 › 输入法 › 编辑…**」的列表里，
「小鹤音形」那行的徽标明显比系统自带输入法小一圈。

**实测**（对真机截图逐像素量）：

| 行 | 徽标实测 | 换算 |
|---|---|---|
| 简体拼音（「拼」） | 44 px 宽 | 正常徽标 |
| 小鹤音形（0.5.0） | **26×26 px** | 正方形，与 `.icns` 的 `icon_16x16@2x` 帧像素一致 |

不是「小一点」，是**内容都对不上**：把截图徽标放大与 `iconutil -c iconset` 解出来的 icns 16px 帧并排，
字形轮廓完全吻合 —— 列表在用 **app 图标**，模式图标压根没被采用。

**排除了什么**（逐项实测，不是猜）：

| 检查项 | 结果 |
|---|---|
| `tsInputMode*IconFileKey` ×3 | 当时与鼠须管一样**三键都指向同一个 PDF**（0.5.1 起本项已改成「菜单键指 PDF、palette 键指 TIFF」，见 0.7.3） |
| `SimpleFly.pdf` | 页面 22×16 pt、墨迹满幅（黑墨模板画法与鼠须管 `rime.pdf` 相同，但后者页面只有 16×16 pt） |
| TIS `kTISPropertyIconImageURL` | 指向 `SimpleFly.pdf` 且**存在** |
| `tis_register --enable` 重新注册 | 无效 |
| `com.apple.IntlDataCache.le` 缓存 | 里面**没有本 bundle 的条目**（缓存论排除） |

**决定性证据**：同一列表里显示正常的「拼」徽标来自
`/System/Library/Input Methods/SCIM.app/Contents/PlugIns/SCIM_Extension.appex/Contents/Resources/pinyin.tiff`。
逐帧解 TIFF 的 IFD 得到 Apple 自家规格：

| 项 | Apple `pinyin.tiff` | 我们的 `SimpleFly.tiff`（0.5.1） |
|---|---|---|
| 帧数 | **2 帧**：16×16 + 32×32 | 同（16×16@72dpi + 32×32@144dpi） |
| 色彩 | 黑墨 + alpha（模板） | 同 |
| 底板 | **满幅**圆角方形（16px 不透明率 ~49%、边中 `alpha=255`、角 `alpha=0`） | 同（约 38%~49%，取决于字形笔画） |
| 字形 | 挖空（even-odd 同一条路径） | 同 |
| 用途 | 菜单栏 + 设置列表**共用**这一个文件 | 同 |

**结论**：macOS 26 的设置列表**不采用 22×16 的 PDF 模式图标** —— PDF 在菜单栏能用，
不等于设置列表会用（0.4.2 那次是 plist 顶层键导致回退，这次是**格式**问题，两层不同）。

**修法**：`tools/make_icon.m` 加 `--tiff` 按上表生成 `SimpleFly.tiff`，
`Info.plist` 三个 `tsInputMode*IconFileKey` 全指向它（22×16 PDF 保留备用）。
**真机注销重登后已确认生效**：列表徽标与系统自带输入法同款。

**踩的坑（离线验收能发现，别等真机）**：底板留 0.5 px inset 会让整行像素只盖一半
（`alpha` 恒 128）→ 模板渲染成半透明灰边。**底板必须满幅**，靠圆角收边。

![模式图标对比](docs/图标对比_0.5.1.png)

> 左：Apple `pinyin.tiff` 的 16px 帧（参照物）；中：本版 `SimpleFly.tiff`；右：0.5.0 实际被列表采用的 icns 16px 帧。

### 菜单栏图标：为什么比别人窄（0.7.3 修复）

**症状**：菜单栏（状态栏）那个输入法图标，比系统自带「简体拼音」窄一圈。

**怎么量的**（不猜，直接量像素）：`screencapture` 截屏 → 裁出图标所在横条 →
量暗内容的包围盒。**@2x 屏**实测（0.7.3 复核定版）：

| 来源 | 菜单栏实测 | 换算 | 图标来源 |
|---|---|---|---|
| 系统「简体拼音」的「拼」 | **44×31 px** | **22×16 pt** | 系统内置 |
| 鼠须管 Squirrel | 32×31 px | 16×16 pt | 自己的 `rime.pdf`（**MediaBox 16×16**，实测） |
| 本输入法 0.7.2（TIFF） | 32×32 px | 16×16 pt | `SimpleFly.tiff` |
| 本输入法 0.7.3（PDF） | **44×31 px** | **22×16 pt** | `SimpleFly.pdf` ✓ 与系统拼音一致 |

**目标参照物是系统「简体拼音」的「拼」（22×16 pt）** —— 用户能并排对比的就是它。

> ⚠️ **更正一条长期写错的依据**：以前多篇笔记写「鼠须管 `rime.pdf` 也是 22×16 pt」，
> **实测是 16×16 pt**（`/MediaBox[0.0 0.0 16.0 16.0]`，Squirrel 0.15.2），
> 它的菜单栏徽标也只有 32×31 px。22×16 这个规格**与鼠须管无关**，纯粹是照系统「拼」定的。
> 误判的来源大概是**设置列表**：那一行槽位会把 16×16 的源缩放进固定槽位，列表里
> 鼠须管 / ABC / 「拼」都量到 44×32 px —— **列表的实测值不能拿来推断菜单栏**。

**根因**：菜单栏图标读的是**顶层 `tsInputMethodIconFileKey` + 两个 mode 级菜单图标键**
（`tsInputModeMenuIconFileKey` / `tsInputModeAlternateMenuIconFileKey`）。
0.5.1 为了修**设置列表**，把这两个 mode 键**也**改成了 16×16 的方形 TIFF，
并**删掉了顶层 `tsInputMethodIconFileKey`** —— 当时的依据是「鼠须管没有它」，
但**实测鼠须管四个图标键都在**（`tsInputMethodIconFileKey` + 两个 mode 菜单键 + palette 键，
**全部**指向 `rime.pdf`），顶层键确实存在，而且正是菜单栏图标的来源。

系统拿 **PDF 的页面尺寸**当图标的逻辑尺寸（不按像素），所以 22×16 pt 的 PDF → 22×16 pt 图标，
16×16 的 TIFF → 16×16，视觉上就是窄一圈。

**修法：两个文件分工，别混**

| 文件 | 供给谁 | Info.plist 的键 |
|---|---|---|
| `SimpleFly.pdf`（22×16 pt） | **菜单栏** | 顶层 `tsInputMethodIconFileKey` + `tsInputModeMenuIconFileKey` + `tsInputModeAlternateMenuIconFileKey` |
| `SimpleFly.tiff`（16×16 双帧） | **设置列表** | 只给 `tsInputModePaletteIconFileKey` |

**怎么验证改对没改对（0.7.3 就是这么验的，不用注销）**：把图标文件**换个名字**（内容一字不改，
例如 `SimpleFlyMenu.pdf`），三个菜单键指向新名 → 重新构建安装 → 菜单栏图标立刻从
32×32 px 变成 44×31 px，就证明这些键确实在管菜单栏。换回原名又会退回缓存的旧图标（见下）。

**⚠️ 大坑：TIS 按「文件路径」缓存图标。** 同一个路径**改内容不生效**，
`killall SimpleFly` / `killall imklaunchagent` / `killall TextInputMenuAgent`、
切换输入法、`tis_register --enable` **全都刷不掉**。只有两条路：
① **注销重登**（会话级缓存重建）；② **换个文件名**（路径变了 → 缓存 miss → 立刻重载）。
调试阶段用 ② 能省一次注销；正式发版用 ① 就行，因为用户本来就要注销重登。

### 菜单栏「图标 + 名字」：不是我们能关的（0.7.3 查清）

**症状**：菜单栏显示「<图标> SimpleFly」，用户希望只留图标。

**结论：这是 macOS 的全局显示项，不是本输入法的问题。** 系统自带「简体拼音」同样显示
「拼 简体拼音」，第三方输入法一视同仁。

**打开/关闭的办法**：点菜单栏的输入法图标 → 菜单里点「**隐藏输入法名称**」
（想恢复就点「显示输入法名称」）。

**怎么找到这条的**（因为是系统内置项，任何工程资料里都查不到）：

1. 系统设置 › 键盘 › 文字输入 里**没有**这个开关。`KeyboardSettings.appex` 的
   `Localizable.loctable` 里跟输入法有关的只有 `Show Input menu in menu bar`（在菜单栏中显示输入法菜单），
   没有任何「名称」相关的项 —— 说明它不在设置面板里。
2. 改从菜单去查：`TextInputMenuCore`（`/System/Library/CoreServices/TextInputMenuCore.bundle`）
   里有 `showHideSourceNameMenuSelected:`、`fShowSourceNameString` / `fHideSourceNameString`
   两个 ivar，以及通知名
   `AppleTextInputMenuUserRequestedTo{Show,Hide}SourceNameInMenuBarNotification` ——
   说明这是**输入法菜单里的一项动态菜单项**。
3. 最后在 `TextInputMenuCore.bundle/Contents/Resources/Localizable.loctable` 里查到原文：

   | key | 简体中文 |
   |---|---|
   | `Hide Name of Source in Menu Bar` | **隐藏输入法名称** |
   | `Show Name of Source in Menu Bar` | **显示输入法名称** |

**顺带验证了两条死路**（省得下次再试）：

- `defaults write com.apple.TextInputMenuAgent AppleShowInputSourceNames -bool false`
  + `killall TextInputMenuAgent` —— **无效**（这个键不存在，系统也不读它）。
- `notifyutil -p AppleTextInputMenuUserRequestedToHide...` —— **无效**，它是进程内
  `NSNotification`，不是 Darwin notify。

|---|---|---|

根因：**「应用图标只在 Finder 里彩色渲染，所以要实心白字」这个前提是错的**。
输入源列表在拿不到模式图标时会**回退到 app 图标**，而它**同样按模板图渲染**（只看 alpha）。
实心 `.icns` 的 alpha 恒为 1 → 被系统涂成一整块。判据不是猜的 —— 拿同机鼠须管的
`RimeIcon.icns` 当参照物，解出来量 alpha 是「不透明 46.5% / 全透明 47.8%」的挖空图。

定位方法（**不依赖真机屏幕**，全靠离线量数据）：

1. 量截图：正常图标 **44×32 px = 22×16 pt @2x**；坏的是 **26×26 px 且内部像素方差为 0**（= alpha 恒 1）。
2. 反推文件：`16 pt 槽位 × 0.804（824/1024）≈ 12.9 pt ≈ 26 px` → 正是 **app 图标**的内容尺寸；
   若用的是模式图标（22×16 pt）就该量到 44×32。**尺寸能反推是哪个文件在被用。**
3. 逐个验文件：`SimpleFly.pdf` 内容流是 `h f*`（正确）、`sips` 能解码、与 `rime.pdf` 四列渲染一致 → PDF 无罪。
4. 找对照物：`iconutil -c iconset` 解双方 `.icns` 量 alpha → 差异锁定在「挖空 vs 实心」。
5. 旁证：Apple 自家 `SCIM.app` 的应用图标是**正方**（927×905）、模式 tiff 甚至不存在却显示 22×16
   → 列表**优先用模式图标、拿不到才回退 app 图标**；
   另 `iconRef` **不能当判据**（我们的和鼠须管的都是空）。

> 代价：挖空后 Finder 深色背景下字形对比度差（浅色背景正常）。本输入法是 `LSUIElement`
> 代理程序、没有 Dock 图标，除了「输入法」列表几乎看不到它，所以按鼠须管的做法处理。

**为什么必须换成 `handleEvent:`**：`IMKInputController.h` 的原文写得很清楚 ——

> there are three ways to receive events here. An input method should **choose one of those ways** and
> implement the appropriate methods: 1. `inputText:client:` + `didCommandBySelector:client:`；
> 2. `inputText:key:modifiers:client:`；3. `handleEvent:client:`

三条路**互斥**。旧版走第 1 条，而修饰键不产生 `keyDown` —— 系统只会给出 `flagsChanged`，
`flagsChanged` 只走 `handleEvent:`，所以第 1 条**永远收不到「单敲 Shift」**。中英一键切换必须要它。

代价：`recognizedEvents` 不再等于默认的 `NSKeyDownMask`，IMK 那套「鼠标点在组合区外自动结束组字」
的默认处理会失效（Apple 文档明说只对「只返回 NSKeyDownMask」的输入法生效），
所以 0.3.0 自己实现了 `mouseDownOnCharacterIndex:…`。同时收 `FlagsChanged` 与 `LeftMouseDown`。

**metro 主题的色值要注意是 BGR**：Rime 的配色写的是 24 位 **BGR**（`0xBBGGRR`）。
`hilited_candidate_back_color: 0xe89f00` 看着像橙色，实际是 **`#009FE8`（青蓝）**。
判断依据不是猜：它的 `hilited_candidate_text_color` 是 `0xffffff`、`label` 是 `0xeeeeee` ——
浅色文字只可能压在深色底上。这条已经写进 `src/SFCandidatePanel.m` 的注释，免得下次再换算错。

在 `src/SFCandidatePanel.m` 顶部可以逐条看到映射：

## 换台 Mac / 移植到 Intel 机型

> 本机是 **Mac mini（Apple 芯片，arm64）**。这一节回答「能不能搬到一台 Intel Mac 上用」。

**能，但要带着源码在那台机器上重新编译 —— 装好的输入法不能直接拷过去。**

### 为什么不能拷

两边说的是两种芯片指令，二进制互不通用：

| 机器 | 这里跑的二进制 | 拷过去的结果 |
|---|---|---|
| 本机 Mac mini M4 | `arm64` | — |
| Intel Mac | `x86_64` | arm64 的 `.app` **根本加载不起来**（Rosetta 只做「Intel 程序跑在 Apple 芯片上」这一种反向翻译） |

实际表现就是：迁移助手把 `~/Library/Input Methods/SimpleFly.app` 原样搬过去，添加输入法后一切照常，但**打不出字**。所以别拷已装的 app，拷源码。

好在**源码本身与芯片无关**：引擎是纯 C、界面是 Objective-C，没有任何按架构分叉的代码；码表是 UTF-8 纯文本；图标是构建时现画的（`make_icon` 依赖的 PingFang 字体两台机器都有）。换机器要改的代码量是 **0**。

### 前置条件

| 条件 | 要求 | 说明 |
|---|---|---|
| 目标机系统 | **macOS 11 Big Sur 或更高** | 项目最低部署目标就是 11.0；Intel Mac 最高只能升到 macOS 15 Sequoia，区间吻合 |
| 编译工具 | 装 **Command Line Tools** 即可，**不需要 Xcode** | `xcode-select --install` |
| 要搬的文件 | 整个 `simplefly/` 目录里的源码与资源 | `src/` `resources/` `tools/` + `build.sh` `install.sh` `uninstall.sh` + `resources/simplefly.dict` |
| 不用搬 | `build/` 整个目录 | 里面是本机产出的 arm64 二进制和 `.app`，留着反而会误事 |

> `resources/simplefly.dict` 那份 76,515 条的码表已经是成品，换机器不必重跑 `tools/build_dict.py`（那条路要再去拉 rime-flypy 上游仓库）。

### 操作步骤

```bash
# ① 在 Intel 机上，把源码目录放好后：
xcode-select --install                 # 已装过会提示 already installed，可跳过
cd <放源码的目录>/simplefly

rm -rf build                           # 关键：清掉可能夹带过来的 arm64 产物
./build.sh --test                      # 六套单测应全部通过
./build.sh                             # 编译 + 组装 .app + 本机签名（几秒）
./install.sh                           # 装到 ~/Library/Input Methods/（不要 sudo）
```

然后回到用户手册 §二第 2 步：**注销重登 → 系统设置里添加 → 首次点「允许」**。

```bash
cd /path/to/simplefly
SIMPLEFLY_ARCH=x86_64 ./build.sh --test     # 交叉构建 + Rosetta 下跑全套单测

```

| 套件 | 项数 | 结果 |
|---|---|---|
| 引擎 | 18 | 全通过 |
| 引擎反查 | 18 | 全通过 |
| 标点 | 58 | 全通过 |
| 拼音键位表 | 74 | 全通过 |

换芯片最常见的坑是 `char` 的符号性差异（Apple 芯片默认无符号、Intel 默认有符号），而这点代码里已经处理掉了 —— 关键位置都显式转成 `unsigned char`。所以预期是全绿，真跑出来也确实全绿。

### 边界与未验证项

- **目标机系统是 macOS 10.15 或更低时不可用**：`Info.plist` 里的 `LSMinimumSystemVersion` 是 11.0，系统会直接拦住启动。此时需要下调最低系统版本重新编译，这条路我没有实测过。
- **别用 AirDrop / 网盘传 `.app`**：除了架构不对，还会带上「隔离」标记，被 Gatekeeper 拦一道。自己在这台机器上 `./install.sh` 出来的（本机 ad-hoc 签名）没有这个问题。
- 上述 Intel 上的实操步骤是**在本机 x86_64 交叉验证结论上推出来的**，尚未在真正的 Intel 硬件上跑一遍。
